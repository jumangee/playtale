# jsIQ Bot — анализатор сторигеймов

Система для виртуального «прохождения» игр на движке jsIQ. Она запускает
оффлайн-версию движка, загружает в неё игру из XML-файла и прогоняет по игре
бота, который делает случайные выборы и записывает пройденный путь в `path.txt`
(при `--runs N` — в `path1.txt` … `pathN.txt`).

> **Что это и чего это не касается.** Это **инструмент исследования формата**, а
> не часть прошивки. Ни один его файл не собирается в образ устройства: он
> существовал, чтобы измерить формат игр, и на его выводах построен серверный
> конвертер и рантайм прошивки. Как игра доходит до экрана читалки, описано в
> [ARCHITECTURE.md](ARCHITECTURE.md) и в
> [docs/contributing/architecture.md](../contributing/architecture.md#storygames);
> форматы хранения на карте памяти — в
> [docs/file-formats.md](../file-formats.md#storygames-on-the-sd-card).
>
> Скрипты лежат в подкаталоге [`examples/`](examples/), а не рядом с этим файлом.
> Всё, что ниже, выполняется из `docs/storygames/examples/`.
>
> **Чего в репозитории нет.** `gamedata.xml`, `gamedata2.xml`, `gamedata3.xml`,
> `gamedata4.xml`, `gamedata_wrong.xml`, `test-mechanics.js`, `path.txt` и
> `play.bat` в репозиторий не входят: это рабочие файлы исследования, и игру для
> прогона нужно положить самому. Вместо них в `examples/` лежат три реальные игры
> и их сконвертированные версии:
>
> | Файл | Что это |
> |------|---------|
> | `gamedata-example1.xml` | исходник игры (`/data/`), 68 параграфов |
> | `gamedata-example2.xml` | исходник игры, 59 параграфов |
> | `gamedata-example19568.xml` | исходник «Портал Зла», 411 параграфов |
> | `playtale-example1.xml` | та же игра после конвертера (`g="12" i="53" p="67" f="0"`) |
> | `playtale-example3.xml` | сконвертированная игра (`g="4" i="29" p="240" f="1"`) |
> | `playtale-example19568.xml` | «Портал Зла» после конвертера (`g="4" i="42" p="410" f="4"`) |
> | `storygames-list-new-example.json` | один снятый ответ каталога |
> | `game_tpl.xml` | эталонный фреймворк платформы, который рантайм повторяет |

## Состав

Все пути — относительно `docs/storygames/examples/`.

| Файл | Назначение |
|------|------------|
| `index.js` | точка входа (CLI). Создаёт `JsiqHosterApp` и запускает прохождение. |
| `jsiq-hoster-app.js` | класс `JsiqHosterApp`: читает файл игры, создаёт движок, запускает бота, сохраняет историю. |
| `jsiq-bot.js` | класс `JsiqBot`: стратегия выбора и запись шагов/изменений параметров. |
| `jsiq-engine.js` | оффлайн-движок `jsIQ` (порт `jsiqapi212.js` 2.1.2) + заглушки браузерного окружения. |
| `dom.js` | минимальный XML DOM + jQuery-подобная обёртка + парсер XML. |
| `jsiqapi212.js` | исходный браузерный движок (для справки, не используется при запуске). |
| `game_tpl.xml` | шаблон mitril, вырезанный из реальной игры: эталон поведения платформы. |
| `cover_convert.php` | серверный конвертер обложки в 1-битный BMP того размера, который просит страница игры. |

## Запуск

Из `docs/storygames/examples/`:

```bash
# положите файл игры рядом и укажите его явно
node index.js --game gamedata-example19568.xml --out path.txt --max-steps 500
# альтернативная стратегия (предпочитать ещё не посещённые параграфы):
node index.js --game gamedata-example1.xml --strategy novelty --max-steps 2000
# 10 независимых прогонов одной игры: path1.txt … path10.txt
node index.js --game gamedata-example2.xml --max-steps 1000 --runs 10
```

`path.txt` (или `path1.txt` … `pathN.txt`) пишется в текущий каталог и в
репозиторий не добавляется.

Файл игры может быть как обычным XML, так и сохранённой страницей
«View Source» браузера (`<!DOCTYPE html>…`) — хост сам распознаёт формат и
извлечёт XML.

## Несколько прогонов (`--runs`)

`--runs <n>` (по умолчанию `1`) задаёт, сколько раз прогнать одну и ту же игру.

- Каждый прогон начинается с чистого листа: создаётся новый экземпляр
  `JsiqHosterApp`, а значит новый движок (состояние `vars` сбрасывается) и новый
  бот. Поэтому выборы в прогонах независимы, а `--strategy novelty` считает
  посещения параграфов заново.
- Каждый прогон сохраняется в свой файл: номер вставляется перед расширением
  базового имени из `--out`. `--out path.txt --runs 10` → `path1.txt` … `path10.txt`,
  `--out runs/try.txt --runs 3` → `runs/try1.txt`, `runs/try2.txt`, `runs/try3.txt`.
- При `--runs 1` (по умолчанию) файл называется ровно так, как указано в `--out`
  (то есть `path.txt`) — прежнее поведение сохранено.
- Ошибка в одном прогоне не прерывает остальные: она печатается в консоль,
  остальные прогоны выполняются до конца, а код возврата процесса становится `1`.

Пример: 10 прогонов `gamedata-example2.xml`, результат — `path1.txt` …
`path10.txt`.

## Как это работает

1. `JsiqHosterApp.loadGame()` читает файл из `--game`, при необходимости
   извлекает чистый XML и передаёт его в движок.
2. Движок (`jsiq-engine.js`) парсит XML, регистрирует обработчики книги и
   выполняет скрипты игры точно так же, как браузерная версия (те же события
   `preload`/`onload`/`unload`, то же окружение скриптов `vars`/`arg`/`local`,
   та же проверка условий `if`/`ifnot`).
3. `JsiqBot.play()` заходит в стартовый параграф и в цикле:
   - читает текст и список доступных вариантов;
   - выбирает вариант (`chooseAction`);
   - выполняет скрипт выбора (`do`) и переход (`goto`);
   - фиксирует снимки состояния до/после и вычисляет diff.
4. Когда доступных вариантов нет — игра считается завершённой, история
   форматируется и сохраняется в `path.txt` (или в `path1.txt` … `pathN.txt` при
   `--runs N`).

## Что записывается в историю

Для каждого шага: текст параграфа, список доступных вариантов, выбранный
вариант, а также изменения игровых параметров отдельно:
- **при входе в параграф** (эффекты `unload`/`preload`/`onload`);
- **при выборе варианта** (эффекты скрипта `do`).

В историю попадают только игровые параметры (`vars.items`), и выводятся они
человеко-понятными именами (например, `Успех / Победные очки: 0 -> 1`).
Системные поля (`steps`, `lastarticle`) и uuid вариантов/параметров не пишутся.

### Видимость параметров

Группы параметров описываются в `rawSetup` (настройка mitril в `onload`
параграфа `mitril`), и у каждой группы есть флаг `visible`. В прохождение
попадают изменения только тех параметров, **чья группа помечена
`visible: "true"`** — то есть ровно то, что игрок видит в «листе персонажа».
Параметры из невидимых групп (скрытые механики, служебные маркеры, вложенные
счётчики) в вывод не попадают, хотя внутри бота по-прежнему отслеживаются
(`history[i].enterChanges` / `choiceChanges` хранят полный diff).

Если у игры вообще нет `rawSetup` (не-mitril книга), фильтр по группам не
применяется и показываются все параметры — иначе выводить было бы нечего.

Флаги (`type "k"`) печатаются как `нет -> есть`, счётчики — числами.

## Кастомизация

### Своя стратегия выбора

```js
const { JsiqBot } = require('./jsiq-bot');

class MyBot extends JsiqBot {
    chooseAction(availableActions, context) {
        // context: { article, engine, stepIndex, availableActions }
        // верните нужный вариант; например, первый с определённым текстом:
        return availableActions.find(a => /нужный текст/.test(a.text)) || availableActions[0];
    }
}

const app = new JsiqHosterApp({ BotClass: MyBot });
```

### Свой формат сохранения

```js
const app = new JsiqHosterApp({
    formatter(bot, hoster) {
        return JSON.stringify(bot.history, null, 2); // вместо текстового path.txt
    },
});
app.run();
```

### Несколько прогонов из кода

```js
const app = new JsiqHosterApp({ gameFile: 'gamedata-example2.xml', outputFile: 'path.txt' });
const results = app.runAll(5); // path1.txt … path5.txt, у каждого свой движок и бот
for (const r of results) {
    console.log(r.runIndex + ': шагов ' + r.bot.history.length + ' -> ' + r.outputFile);
}
```

`runAll(n)` возвращает массив результатов (те же поля, что у `run()`, плюс
`runIndex` и `runsTotal`); при ошибке прогона в его результате будет поле `error`.

### Свои хуки

`JsiqBot` предоставляет `onStep(step)` и `onFinish(result)`, которые можно
переопределить, чтобы стримить шаги или агрегировать статистику.

### Детерминированные прогоны (тесты)

```js
const app = new JsiqHosterApp({
    botOptions: { random: () => 0.5 }, // фиксированный источник случайности
});
```

## Замечания по совместимости

- Движок синхронный (в браузере события шли через `setTimeout` для отрисовки
  UI) — на игровую логику это не влияет.
- Сетевые запросы (`$.ajax` на сервер quest-book) заменены оффлайн-заглушками:
  `getSavegame` считает, что сохранения нет (игра начинается с начала),
  сохранение/достижения — no-op. Поэтому состояние `vars` у бота соответствует
  «анонимному игроку без сохранений».
- `exprEval` (для условий вида `{"type":"s"}`) и `Base64` представлены
  заглушками. `Base64` реализован полноценно (нужен задачам `class:"if"`,
  `type:"64"`). `exprEval` — заглушка; в приложенных играх условия типа `s`
  не встречаются (только `k`, `r` и `f`). Это ограничение **бота**, а не
  прошивки: рантайм на устройстве вычисляет `s`-выражения по-настоящему
  (`TextEvaluator` в `lib/QuestBook/StorygameEngine.cpp`), и в корпусе из 35 игр
  они встречаются в 4 играх — см. [ARCHITECTURE.md](ARCHITECTURE.md) §1.3 и §5.3.
- `type:"f"` в данных — это не отдельный тип условия, а поле `type` у задачи
  `class:"fun"`; движок исполняет такую задачу через `mitrilSetup.functions`.
